# Nekto Text Hub

A hosted, phone-friendly dashboard with two native conversation panels. Click Connect for A and B, or Connect both, to start the site's searches automatically. Each panel shows that stranger's messages and what was sent to them. Forwarding starts automatically when both strangers are connected. There are no screenshots or remote browser controls.

Incoming messages are forwarded unchanged to the other connected session. No greetings, labels, prefixes, suffixes, or extra automatic messages are sent. Each panel's message box sends only to that panel's stranger; operator messages are not copied to the other side. Enter sends and Shift+Enter inserts a newline. Conversation history is held in memory and cleared when that conversation changes. When a stranger ends their conversation, that session closes automatically; the other side stays open. Reconnect manually when ready. The authToken form remains visible after sign-in and applying tokens.

Two isolated Chromium contexts run the text client at https://nekto-me.kz/chat/. Conversation changes invalidate old deliveries, queues cap at 40 messages and expire after 30 seconds, and sends are spaced by 1.1 seconds. The native text client uses `chat.anonDialog` and its existing `anonMessage` action. Sender IDs exclude outgoing echoes, stable message IDs prevent duplicate forwarding, and the sender waits for the server's matching message ID before confirming delivery. DOM detection remains a compatibility fallback. Chat text is not written to application logs.

## Deployment

The Dockerfile includes Playwright's matching Chromium binaries. Set a private `DASHBOARD_PASSWORD` of at least 16 characters and optionally `TEXT_DATA_DIR=/data/text-host`. Railway supplies `PORT`. Attach a volume at /data for session cookies and local storage. The previous voice bot's settings are unused; its source remains in Git history and a backup branch.

Run `npm install`, then `DASHBOARD_PASSWORD=your-private-long-password npm start`. Run `npm test` for adapter, bidirectional forwarding, private-message isolation, stale-conversation, and token-storage tests. The dashboard works in Android Chrome as a hosted web app.

## Existing session tokens

The optional token form accepts two distinct authTokens from your own Nekto sessions. Applying them reuses each existing browser page, imports each token into its live client, and starts both searches automatically. Pending deliveries and panel histories are cleared during a token change. Tokens are submitted in authenticated request bodies and omitted from logs and status responses. The form keeps both values after Apply, including failures, and restores saved values through an authenticated endpoint after reopening the page. Saved fields are preserved. After the text client loads, the app commits `user/setAuthToken` to its running Vuex store and calls its existing `authorize()` method. It waits for `user/socket_auth.successToken` and checks that the supplied token remains in both live state and `storage_v2`. The known `storage_v2.user.authToken` is seeded before a fresh page loads. Token preparation makes two sequential normal authorization requests on the same page, confirming each response or checking that an existing server-issued matching identity remains authenticated and connected after two seconds before search. The latter is logged as existing-session-confirmed rather than a new server acceptance. It does not refresh the page. Prepared sessions are reused on subsequent Connect operations. A verification requirement stops the sequence immediately. The explicitly entered pair is saved atomically in a private file on the volume and restored after restart. Token replacement or timeout stops that connection and reports an error. Persistent verification stops the search; there is no automatic refresh loop. Session storage persists on the server volume.

A token import does not prove the site accepted the token or guarantee that verification is skipped. If Nekto requires CAPTCHA or blocks the hosting address, the panel reports that status. This dashboard cannot complete that verification. Live matching depends on the site's acceptance and availability; passing the application tests does not establish a live stranger connection.

## Video chat

The `/video` tab runs two separate hosted OmeTV contexts. Paste each of your own signed-in sessions' complete `snid` JSON into the always-visible A/B fields, then click **Применить и подключить A + B**. Obtain it in each of your own signed-in OmeTV browser consoles with `copy(localStorage.getItem('snid'))`. Paste credentials only into your password-protected dashboard, never into chat or issues. No login screenshot or browser-control window is exposed.

OmeTV's public account client stores `{token, SnDataStr, SnHmac}` in `snid` and delivers these fields to its embedded chat as `{setAuthToken, videochatDataStr, videochatHmac, source:'sn'}`. The import preserves the signed strings exactly. A bare token, Nekto token, or missing signature is rejected. Profiles are saved in a private file with mode 0600, independently from text tokens. They are omitted from status responses and logs. The authenticated session endpoint restores them into the fields; applying them keeps the entered values visible.

The host loads the native OmeTV chat document directly to avoid two heavy account homepages within the 1 GB service limit. It seeds the saved profile before loading and stores the profile twice and delivers one native signed session message to that document before clicking Start. The native client and its verification controls are retained. It follows native iframe replacement after authorization, waits for the new chat controls, and reacquires the current frame before Start. Start targets the native clickable button container by its translation key, rather than its noninteractive text span; this is covered by the Chromium regression fixture. It stops if verification appears or the client retains its login prompt. Closing and reopening a video side restores its saved profile. Client acceptance of the envelope is not proof of a successful server-authorized call; invalid or expired sessions can still be rejected by OmeTV. Importing credentials does not bypass site verification.

Recognize your two consenting friends, confirm both know about the bridge, then click **Соединить участников**. Their camera frames and audio are forwarded both ways. Each panel's text field sends only to that side. A participant ending their call closes that video session and disables forwarding. The text tab works independently.

Incoming site streams are encoded in memory with VP8/Opus, transported through the authenticated application connection, and decoded into the opposite session's virtual camera and microphone. The dashboard shows actual live media in plain call panels with separate sound buttons, without playback controls. Media buffers are bounded and never saved to disk. Encoding and decoding add latency.

Authenticated `POST /api/video/test` checks both video directions and both audio directions with generated colored frames and distinct tones. It requires real video sessions to be closed, creates disposable local fixtures, reports numeric diagnostics, and closes them afterward. It never starts OmeTV matching or contacts a person. The iframe replacement sequence is covered by a real Chromium fixture test in the Railway build. Saved native session imports were also checked without starting matching; live calls remain a separate check.

## Nekto audio calls

Open `/audio` and use the existing dashboard password. Audio has its own always-visible token fields and independent saved token file. Use two distinct tokens from your own Nekto **voice** sessions: `JSON.parse(localStorage.getItem('storage_audio_v2')).user.authToken` in each regular voice browser. Paste them into this dashboard, not into chat. Applying them saves the pair privately and starts both native voice searches. Later, **Подключить A + B** reuses the saved pair. Voice uses `https://nekto-me.kz/audiochat`; text tokens are not automatically copied into voice.

Audio uses two Chromium processes with native microphone permissions. A private PulseAudio server provides independent virtual microphones and outputs; opposite-direction loopbacks route A's received audio to B's microphone and B's received audio to A's microphone. The browser's media APIs and verification controls remain intact. No video encoder, camera permission, browser screenshot, automatic spoken greeting, or recording is used. Site playback, including its own sound effects, is part of the output stream.

Both participants must consent to the bridge. Check the consent box when connecting them; routing unmutes only while both native sessions are connected and consent is enabled. A stranger ending their call closes that side automatically and mutes both routes. The other side remains open. Click **Слушать A/B** to hear an optional live preview; volume affects your preview only. Audio preview packets remain in bounded memory, and slow subscribers are disconnected. Closing a session discards its preview and stops capture.

Native authorization is confirmed before pressing the site's Start button. A fresh page restores `storage_audio_v2` before initialization, then uses the client's normal `user/setAuthToken` and `authorize()` only if the restored identity is not already authenticated. There is no refresh loop. A CAPTCHA, hosting restriction, or authorization timeout stops that side and reports it. Tokens alone cannot guarantee site acceptance.

The current Railway memory limit supports one active mode at a time: close text/video sides before starting audio. `tests/audio-host.test.js` checks consent, disconnect muting, capture isolation, and authorization. `tests/audio-devices.test.js` runs in the Docker build with real PulseAudio and native Chromium microphones; generated 440/880 Hz tones test both directions and muting without contacting Nekto or any person. That verifies media routing, not live stranger matching.

### Audio meters and authorization diagnostics

Each audio panel has an independent sound meter measured from PCM16 browser output. It shows a bounded dBFS scale, falls to zero on silence/disconnect, and runs without enabling dashboard listening. Captures are shared with preview subscribers rather than duplicated, stop when a disconnected side has no listeners, and never write audio to disk. Site sounds may also move the meter.

Normal voice authorization waits for a connected socket and the native registration state to settle before Start. It sends at most one request, never refreshes, and stops on verification. Structured logs contain only the phase and boolean token/state checks; no tokens or identity IDs are logged. Correct stored tokens and authenticated state can coexist with a site-required CAPTCHA; the client preserves that requirement.
