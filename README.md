# Nekto Text Hub

A hosted, phone-friendly dashboard with two native conversation panels. Click Connect for A and B, or Connect both, to start the site's searches automatically. Each panel shows that stranger's messages and what was sent to them. Forwarding starts automatically when both strangers are connected. There are no screenshots or remote browser controls.

Incoming messages are forwarded unchanged to the other connected session. No greetings, labels, prefixes, suffixes, or extra automatic messages are sent. Each panel's message box sends only to that panel's stranger; operator messages are not copied to the other side. Enter sends and Shift+Enter inserts a newline. Conversation history is held in memory and cleared when that conversation changes. When a stranger ends their conversation, that session closes automatically; the other side stays open. Reconnect manually when ready. The authToken form remains visible after sign-in and applying tokens.

Two isolated Chromium contexts run the text client at https://nekto-me.kz/chat/. Conversation changes invalidate old deliveries, queues cap at 40 messages and expire after 30 seconds, and sends are spaced by 1.1 seconds. The native text client uses `chat.anonDialog` and its existing `anonMessage` action. Sender IDs exclude outgoing echoes, stable message IDs prevent duplicate forwarding, and the sender waits for the server's matching message ID before confirming delivery. DOM detection remains a compatibility fallback. Chat text is not written to application logs.

## Deployment

The Dockerfile includes Playwright's matching Chromium binaries. Set a private `DASHBOARD_PASSWORD` of at least 16 characters and optionally `TEXT_DATA_DIR=/data/text-host`. Railway supplies `PORT`. Attach a volume at /data for session cookies and local storage. The previous voice bot's settings are unused; its source remains in Git history and a backup branch.

Run `npm install`, then `DASHBOARD_PASSWORD=your-private-long-password npm start`. Run `npm test` for adapter, bidirectional forwarding, private-message isolation, stale-conversation, and token-storage tests. The dashboard works in Android Chrome as a hosted web app.

## Existing session tokens

The optional token form accepts two distinct authTokens from your own Nekto sessions. Applying them reuses each existing browser page, imports each token into its live client, and starts both searches automatically. Pending deliveries and panel histories are cleared during a token change. Tokens are submitted in authenticated request bodies, cleared from the form, and omitted from logs and status responses. Saved fields are preserved. After the text client loads, the app commits `user/setAuthToken` to its running Vuex store and calls its existing `authorize()` method. It waits for `user/socket_auth.successToken` and checks that the supplied token remains in both live state and `storage_v2`. The known `storage_v2.user.authToken` is seeded before a fresh page loads. Token preparation makes two sequential normal authorization requests on the same page, confirming each response or checking that an existing server-issued matching identity remains authenticated and connected after two seconds before search. The latter is logged as existing-session-confirmed rather than a new server acceptance. It does not refresh the page. Prepared sessions are reused on subsequent Connect operations. A verification requirement stops the sequence immediately. The explicitly entered pair is saved atomically in a private file on the volume and restored after restart. Token replacement or timeout stops that connection and reports an error. Persistent verification stops the search; there is no automatic refresh loop. Session storage persists on the server volume.

A token import does not prove the site accepted the token or guarantee that verification is skipped. If Nekto requires CAPTCHA or blocks the hosting address, the panel reports that status. This dashboard cannot complete that verification. Live matching depends on the site's acceptance and availability; passing the application tests does not establish a live stranger connection.

## Video chat

The `/video` tab runs two separate hosted OmeTV browser contexts. It does not reuse Nekto tokens or the assistant's cloud-browser sign-in. Use **Вход в OmeTV** on each side to complete the provider's normal sign-in in the temporary browser window. **Сохранять вход на сервере** is optional and saves that context's session cookies and local storage on the private server volume. With it off, video sign-in lasts only while that browser context remains open.

Click **Подключить** on each side, recognize your two consenting friends, confirm both know about the bridge, then click **Соединить участников**. Their camera frames and audio are forwarded both ways. Each panel's text field sends only to that side. A participant ending their call closes that video session and disables forwarding. The text tab continues to work independently.

Video uses canvas-backed virtual camera tracks and Web Audio destinations. Incoming site streams are encoded in memory with VP8/Opus, transported through the authenticated application connection, and decoded into the opposite session's virtual media input. The dashboard receives these same live media segments, rather than screenshots of the chat page. Media buffers are bounded and are not saved to disk. Dashboard players start muted; enable sound in their player controls. Expect added latency from decoding and encoding.

The browser window is shown only for user-operated sign-in, including provider popups. It does not automate account creation, accept provider terms, solve verification, or hide automation. OmeTV or its sign-in provider may reject the hosted environment; in that case, inspect the user-visible error and stop. A working local login does not establish that these separate hosted sessions will be accepted.

Authenticated `POST /api/video/test` exercises both video directions and both audio directions with generated colored frames and distinct tones. It requires both real video sessions to be closed, creates disposable local fixture pages, reports numeric diagnostics, and closes them afterward. It never starts OmeTV matching or contacts a person.
